# React + TypeScript + Vite

This template provides a minimal setup to get React working in Vite with HMR and some Oxlint rules.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Oxc](https://oxc.rs)
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/)

## React Compiler

The React Compiler is not enabled on this template because of its impact on dev & build performances. To add it, see [this documentation](https://react.dev/learn/react-compiler/installation).

## Expanding the Oxlint configuration

If you are developing a production application, we recommend enabling type-aware lint rules by installing `oxlint-tsgolint` and editing `.oxlintrc.json`:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "typescript", "oxc"],
  "options": {
    "typeAware": true
  },
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

See the [Oxlint rules documentation](https://oxc.rs/docs/guide/usage/linter/rules) for the full list of rules and categories.

## Site tabs

The site is a static SPA (no backend) with four tabs: **About** (bio + Articles,
with comments/likes), **Marketplace** (downloadable agent/skill packs),
**System Design** (architecture diagrams), and **Lab** (a live multi-agent
orchestrator demo). Everything works out of the box with zero configuration,
using localStorage. Two pieces have an optional "real AWS" mode:

### Making comments/likes/download-counts shared across visitors (S3)

By default, article comments/likes and marketplace download counts are stored
in each visitor's localStorage only. To make them genuinely shared (via
`src/lib/remoteStore.ts`), provision:

1. An **S3 bucket** (no public read/list needed).
2. A **Cognito Identity Pool** with unauthenticated access enabled, whose
   guest IAM role allows only:
   ```json
   {
     "Effect": "Allow",
     "Action": ["s3:GetObject", "s3:PutObject"],
     "Resource": "arn:aws:s3:::YOUR_BUCKET/articles/*"
   },
   {
     "Effect": "Allow",
     "Action": ["s3:GetObject", "s3:PutObject"],
     "Resource": "arn:aws:s3:::YOUR_BUCKET/marketplace/*"
   }
   ```
   Deliberately no `s3:ListBucket` and no `s3:DeleteObject` — visitors can add
   data but not enumerate or destroy it.
3. A **CORS configuration** on the bucket allowing `GET`/`PUT` from your site's
   origin.
4. Add a `.env.local` (untracked) with:
   ```
   VITE_AWS_REGION=us-east-1
   VITE_S3_BUCKET=your-bucket-name
   VITE_COGNITO_IDENTITY_POOL_ID=us-east-1:xxxxxxxx-xxxx-...
   ```

Without these, the app silently falls back to localStorage — nothing breaks.

Note: this is a read-then-write counter/list pattern, not atomic. Fine at
personal-portfolio traffic levels; not meant to survive high concurrent write
volume.

### Live Bedrock in the Lab tab

The Lab tab's orchestrator simulation is fully client-side and always works.
Its final summary can optionally be generated by a real Bedrock call: open
"Live Bedrock" in the Lab tab and paste temporary AWS credentials (e.g. from
an STS session) — they're kept in `sessionStorage` only, sent nowhere but AWS,
and cleared when the tab closes. This is opt-in per visitor by design: a
public static site should never ship long-lived AWS credentials in its
bundle. Some Bedrock Runtime endpoints don't allow cross-origin browser
requests; if a live call fails, the run automatically falls back to the local
summary.
